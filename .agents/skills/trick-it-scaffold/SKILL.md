# trick-it tool scaffolding

Read the project recipe at [docs/scaffold-tool.md](../../../docs/scaffold-tool.md) **from the repository root**. Relative to this skill directory, that file is `../../../docs/scaffold-tool.md`. It contains copyable dependency-free HTML, Node builder, manifest and artifact-test examples; no scaffolding CLI is assumed.

## Establish the boundary

1. Identify the tool's operation, ID, category, capabilities, approved GitHub owner/repository and intended source location. Ask only for consequential missing inputs. Search existing registry IDs and source folders before choosing a path; preserve all existing registrations and never overwrite an existing tool scaffold.
2. Inspect the current `src/lib/registry/contract.js`, `src/lib/registry/sandbox.ts`, `config/registry.json`, `config/tools/`, `scripts/lib/registrations.mjs`, `scripts/lib/bundles.mjs` and relevant authentication docs. The implementation is authoritative if the recipe has drifted.
3. Keep the tool independently buildable in its own repository. Keep new production tool HTML, manifest, README and tests in its own repository. Tool-specific browser/host-integration suites also belong there, never under trick-it's test directory; use a compatible host checkout to exercise the real runtime. The host owns only cross-cutting runtime/SDK/permission/security/catalog/site tests. Use `examples/<id>` only for an intentional local development fixture; never create a production mirror by default. Do not import the tool's source/framework into the host or add a runtime API dependency.

## Mandatory shared-UI gate (new and existing tools)

Read [docs/tool-ui-checklist.md](../../../docs/tool-ui-checklist.md) and the `trickIt.ui` section of [docs/tool-runtime.md](../../../docs/tool-runtime.md) before implementation. **This is required, not a styling suggestion.**

- Inventory applicable interactions in the source and rendered tool. Use the provided `ui.fileInput` for file selection/drop/previews, `ui.status` for async job states, `ui.loader` for deferred/external assets and engine initialization, `ui.toast` for transient notices, and host-rendered `ui.info`/`ui.confirm` for popups. `loader.asset(id)` receives verified bytes and real progress; initialization is a separate phase. Do not invent progress percentages.
- When an existing tool does not conform, **modify it in its own repository before release**. Merely recoloring custom controls, adding unused SDK calls, or patching only the host does not complete a migration. Preserve file limits, operations, accessibility, input/output and cancellation; remove redundant hosted markup/styles/listeners.
- Use native/minimal standalone fallbacks only when the relevant shared API is absent, never as a bypass after a capability denial. Do not copy the shared kit into the tool or show both pickers. Unsupported text-only-dialog interactions become inline panels; extend and test the host kit first if a genuinely missing shared component is necessary.
- Require behavioral evidence for every applicable component (selection/drop/refusal, real loading/progress/error/retry, parent-centred dialog/focus, toast). Test locale/theme preservation, 320–375px layouts and remembered permission grant/denial/reset. Mark a component not applicable only when its interaction does not exist; do not add artificial loaders to synchronous tools.
- Visual coherence: verify the shared picker, status card, loader and toasts in the tool's real containers at desktop and 320–375px (centred icon/label/hint/button, identical sizing to other tools, no duplicated or stacked cards, close buttons on finished cards/toasts). Never override the kit's structure; tool CSS must not target `.ti-*` internals.
- Accessibility details that tests must cover: the element passed to `ui.status` must not carry its own `role="status"`/`aria-live` (the card is the live region); an action that opens a host permission dialog stays focusable with `aria-busy`/`aria-disabled` and a re-entry guard (not native `disabled`) so focus returns to it; hosted popups never degrade to in-frame modals when the host is busy.
- **Before any push or re-pin**, update the runtime/scaffold documentation and this skill when APIs or rules change, complete the checklist, and fix every nonconforming hosted interaction. Keep blocked/untested work open. Registry validation does not prove visual or behavioral compliance.

## Mandatory Paraglide and efficient language-pack gate

- Use **Paraglide JS at build time** for every new tool and localization migration. Keep all tool-owned labels, help, errors, status, accessibility text and consent copy in `messages/<locale>.json` with `project.inlang/settings.json`; pin the compiler and message-format plugin in the lockfile/config. Do not maintain handwritten phrase dictionaries or translate by scanning/mutating DOM text.
- Compile catalogs, validate identical nonblank keys before fallback, and project the generated message functions into **one JSON file per supported non-English locale** (`dist/locales/<locale>.json`). Embed generated English fallback only in the HTML; do not bundle all catalogs, generated multi-language runtime modules or an editable source archive containing all catalogs into the bootstrap. Keep source archives as separate verified deferred assets when provided.
- Prefer v3 `localePacks[locale] = { file: "dist/locales/<locale>.json", sha256, bytes }`, separate from `assets` and metadata `translations`. `registry:sync` reads each file from the same pinned repository commit using the existing build-only GitHub PAT, verifies size/hash/UTF-8/message JSON, and stages it at `/bundles/<tool-id>/locales/<sha256>.json` in the Pages output. The runtime derives the same-origin, base-aware URL; no private-repository request or PAT reaches the browser. Files require no external-origin approval. Existing `{ url, sha256, bytes }` packs remain supported for approved public immutable HTTPS hosting; never combine `file` and `url`. Each pack must be 1–65,536 bytes with exact final bytes and lowercase SHA-256. If `localePacks` is present, every declared non-English locale requires a pack; English has no pack. Read [the pack contract](../../../docs/tool-contract-v3.md#language-packs) and [runtime loader](../../../docs/tool-runtime.md#language-packs).
- Load only the selected pack using `window.trickIt.localePack(locale)`, decode/validate JSON, cache parsed packs and deduplicate in-flight requests. This read-only broker requires **no `external-assets` permission** and never enables iframe networking. Reject corrupt packs, clear failed in-flight entries for retry, report failures and keep a readable English fallback without losing work. Guard asynchronous switches so the newest host locale wins.
- Preserve host #101's no-refresh invariant from commit `63a0222e4b9ff88fae590e78d472824b04d9cb48`: client-side host navigation sends `trick-it:localechange` into the **same iframe**. Never reload/navigate/replace its document, reinitialize the editor, or clear input, output, focus, selected files or running jobs. Avoid Paraglide's default `setLocale()` reload behavior; explicit `{ locale }` message evaluation at build time needs no browser navigation. Do not use experimental per-locale full-document builds.
- Require behavioral coverage for initial languages, cached/repeated requests, rapid out-of-order switches, denied unrelated permissions, corrupt/offline packs and retry, both themes and 320–375px layouts. Verify iframe identity and active workspace state. Build twice and compare **all** release files (HTML, packs, source archive and manifest) byte-for-byte; never synchronize artifacts by dumping base64 into CI logs or weakening drift checks. File-based packs must be exercised through the real local host/harness endpoint, not a CDN mock. Deployment publishes HTML and verified packs together; external URL packs still require their immutable URLs to exist.

## Exact-head localization release gate

- Derive required locales from the compatible host's `src/lib/languages.js` `languageCodes`, not a copied language list. Keep compiler settings, authored catalogs, manifest coverage and browser loops aligned. Validate raw key/nonempty/placeholder parity before compiler fallback; verify published flat JSON equals the authored safe string templates. Nested native groups are reconstructed after delivery, never shipped in the host's flat-message protocol.
- Generate native metadata names/descriptions, **quick-start guides** and consent reasons as well as application labels. Every declared non-English locale must have `translations[locale].guide.summary` and `translations[locale].guide.steps`, with the same number and order of meaningful instructions as the canonical English `guide`. Author each summary and step in the tool's Paraglide `messages/<locale>.json` and derive the manifest guide at build time, never from a second handwritten translation dictionary. The release checker verifies **each manifest summary/step occurs verbatim in the corresponding authored catalog**, including English; do not generate an unrelated duplicate dictionary. Do not silently fall back to English, reuse an English instructional sentence, or collapse several steps into one. Preserve technical identifiers/examples where translation would make them incorrect. Inventory initial/help/error/busy/retry/completed and accessibility copy; neither full key counts nor a locale manifest proves coverage or fluent quality. Keep unreviewed localized SEO noindex. English-only teaching fixtures and legacy runtime-compatible inline catalogs are not compliant new production scaffolds.
- Run `node "$TRICK_IT_DIR/scripts/check-tool-release.mjs" --tool-root "$PWD" --baseline origin/main` after `npm ci`, tool tests and real-host browser tests. Fetch the baseline first; omit it only for a first release. The checker derives host locales and enforces authored/published parity, flat packs, **native guide presence, ordered step-count parity and rejection of copied English instructional text**, metadata/consent coverage, exact compiler/plugin pins, lock/version consistency, integrity and a stable version advance. Prerelease ordering requires explicit review. Its structural pass does not certify visible copy, runtime behavior or native-language quality.
- Use the owning local bundle through `tests/tool-harness`, never a stale catalog pin. Its startup runs the full registry manifest schema, not just checksum/pack checks: enforce localized field bounds and complete SEO objects even for noindex copy. Assert actual native messages and the same iframe/contentWindow, active editor/selection, file handles, outputs and pending work through all host locales and back to English on mobile/desktop. Read CI fixture prerequisites and set model/resource paths explicitly. Harness port 4190 suites run sequentially. Test native-picker and buffered Blob stream sinks separately; native saves do not emit browser download events, and every stream begin requires fresh user activation. Do not confuse this with legacy download requests or remembered denial.
- Record exact tested SHA and Node/npm versions. Missing/skipped checks or an ancestor's success are not current-head CI. Billing-only exceptions require explicit authorization, failure annotations proving no runner started, and successful exact-head local checks; never bypass genuine failures or claim billing-blocked CI passed. Diagnose first npm errors; generate missing locks in clean disposable checkouts, then prove normal `npm ci`. Preserve other dependency graphs and ignore generated browser/dependency/temporary-host files.
- Keep the fixed 8,192-byte gzip catalog-entry budget: metadata guides are concise native quick-starts, while complete native help stays in the tool's selected pack/UI. The checker shares the production budget constant; do not raise limits or remove app help to fit a release. Registry sync and test harness also share the same full manifest byte/UTF-8/schema parser. Full multilingual catalog imports stay server-only; serialize active-locale metadata into static route data, retaining native consent/guide copy and iframe identity. Use Paraglide's request-scoped server locale after middleware canonicalizes URLs; track URL navigation explicitly rather than guessing locale from the canonical path.
- Bump semver for localization releases; derive manifest version from package metadata and keep lock metadata aligned. Compare all rebuilt files, then rebuild/verify the actual merge commit before tag/release publication and full-SHA host pinning. Never overwrite a release tag. Preserve registration timestamps and the requested host PR branch. Keep release, PR pin, deployment and editorial approval claims separate.

## Build the tool

- Start with the minimal recipe in the guide or the existing JSON Tools builder for larger dependency-bundled tools. Adapt behavior, labels and limitations to the requested operation; do not ship an unchanged counter under another name.
- Release one self-contained UTF-8 HTML document, including inline scripts/styles/assets, plus `tool.manifest.json`. No direct iframe network requests, secrets, telemetry, unsafe JavaScript evaluation, parent-DOM access or ambient browser privileges. Public external assets must be declared with approved origin, exact size and SHA-256; fetch verified bytes through `window.trickIt.asset(id)` only after host consent. Declare supported capabilities with truthful reasons and use the host request broker; never call privileged parent APIs or add `allow-same-origin`. WASM compilation and blob workers are conditional grants, not blanket JavaScript eval or network access.
- Support trick-it's clay styling, every language actually declared in `locales`, and both themes. The host accepts `en`, `id`, `ms`, `fil`, `th`, `vi`, `zh`, `my`, `km`, `lo`, `ja` and `hi`; do not claim a locale before all tool-owned UI copy is translated. Use `document.documentElement.lang`/`window.trickIt.locale` and listen for `trick-it:localechange`; do not clear input on locale changes. Consume the root `--ot-*` tokens; add `[data-theme="dark"]` rules for any custom colors. The host injects the root theme and its validated, one-way theme receiver. Do not duplicate that receiver, introduce a competing theme toggle/preference, or reload and lose user input on theme changes. Never send user data to the parent.
- Require `schemaVersion: 3`, `runtimeVersion: 1` and `appearance: { theme: "host", protocolVersion: 1 }`. Include icon, version, SEO, guide, permissions, assets and tool-owned metadata translations. Localized consent reasons belong in `translations[locale].permissionReasons`, a bounded map for already declared permissions; never mutate permission declarations on locale changes. Declare actual interface support in `locales` (default English only); set `["en", "id"]` only when the tool translates both interfaces. Read `docs/tool-contract-v3.md`, `docs/tool-runtime.md` and `docs/seo.md`. Legacy v2 tools remain supported without privileged capabilities. The metadata path is exactly `/<id>` without a trailing slash, even though the public route is `/<id>/`.
- Respect reserved IDs and all current contract limits. Keep human-facing metadata truthful. `repository` must match the registered `https://github.com/owner/repository`; `bundle.file` is a safe relative `.html` path. Update SHA-256 from the **exact final HTML bytes** after each build, not before minification or newline changes. Never leave the placeholder digest in a release.
- Keep the bundle below the 5 MiB hard limit and the user-approved 200,000 gzip-byte per-tool ceiling; this is a limit, not permission to embed all languages or editable-source archives. Use the separate-pack approach above. Add input limits, errors that preserve user input, keyboard access, visible focus, 44px targets and reduced-motion support where applicable. Synchronous CPU-heavy code can freeze an iframe/tab; the sandbox is not a CPU isolation guarantee.

## Verify and publish

1. Complete the [shared-UI release gate](../../../docs/tool-ui-checklist.md), including migration of existing nonconforming controls and current skill/API documentation. Run the tool's functional tests and build. Test empty/invalid/large/Unicode inputs as appropriate; artifact checksum smoke tests alone are insufficient. Review the actual HTML for external loads and credential/private-sample leakage.
2. For a standalone release, add `config/tools/<id>.json` with its pinned commit SHA and an `added` UTC timestamp (see `docs/registry-layout.md`), ship the tool's distinct clay art **in the tool repository** (`assets/icon.webp` 160×160 ≤12 kB, optional `assets/card.png` 512×512) and declare it under `artwork` in `tool.manifest.json` with exact `sha256`/`bytes` (see `docs/registry-layout.md`; trick-it keeps no copy and never commits icons), and run `npm run registry:sync`. Keep any temporary local fixture unregistered in production. Test the actual host iframe in both themes, including a live theme change that preserves input/output, mobile layout and keyboard/error states. Add targeted browser regression coverage **in the tool repository**, independent of the catalog's published pin. Keep only generic platform/SDK/catalog coverage in the host. Wire the owner suite with `tests/tool-harness` (`playwright.host.config.mjs`, `test:host`, `@playwright/test` at the host's exact release) and run `TRICK_IT_DIR=<host> npm run test:host`. Derive `tool.manifest.json` `version` from `package.json` in the build and cover version, digest and script syntax in an artifact test.
3. Run host `npm test`, `npm run check`, `npm run build`, `npm run performance:check` and `npm run test:e2e`. The shared-JS budget is enforced per tool (see "Catalog PRs and CI"); never raise a fixed whole-marketplace ceiling to make a registration pass. Install Playwright Chromium only if needed. Report exactly which checks ran and their results; do not imply static review is runtime verification.
4. Before any commit, configure **both author and committer** as `ygrip <yunaz.gilang@gmail.com>`; explicitly verify the resulting commit identity. Do not inherit a corporate global identity. Commit source catalogs/config, manifest, release HTML, every generated language pack, separate source archive (if provided) and dependency lockfile in the same standalone source commit. Never commit `node_modules`, credentials or real private samples. Do not push or rewrite history without authorization.
5. `git fetch` and integrate any concurrent upstream commits first (re-run the tool's suites after a merge), push, and confirm `origin/main` equals the SHA to pin. After the source commit exists on GitHub, add or update only `config/tools/<id>.json` with its repository and full lowercase 40-character SHA; the approved owner stays in the shared trust policy. Local paths cannot point outside `examples/`; remote refs cannot be branch names/tags/short SHAs. Keep discovery disabled unless explicitly authorized. Re-run checks using the intended production configuration, then commit/push the registry change when authorized. Deploy the complete static output atomically.

## Catalog PRs and CI

- One registration per PR/branch (`feat/register-<id>`) touching `config/tools/<id>.json`, the icon pair and nothing else. When several registrations are open, merge them one at a time: `git fetch`, merge `origin/main` into the next branch, resolve conflicts, wait for CI, then merge. Conflicts concentrate in shared files such as `scripts/check-performance.mjs`; keep main's newer logic and never drop either side's registrations.
- Performance budgets live in `scripts/check-performance.mjs` and are **per tool**: each registered tool raises the shared-JS ceiling by `TOOL_JS_ALLOWANCE` gzip bytes above the 18-tool host baseline, a single tool's catalog entry may not exceed `MAX_TOOL_ENTRY_GZIP` (8,192 gzip bytes for localized metadata and consent reasons), tool bundles stay under 200 kB gzip and icons under 12 kB each. If CI reports a JS budget overrun, first check whether host code (not the new tool) grew; change the host baseline only for a deliberate shared-kit addition and say why in the commit.
- Art changes need a new tool commit and a re-pin. Icon URLs are content-hashed and `static/_headers` serves `/icons/tools/*`, `/bundles/*` and `/_app/immutable/*` as immutable, so never put a mutable file under those paths.
- A local `npm run build` needs private-repo read access (`TOOLS_GITHUB_TOKEN` or per-repo credentials, see below). A `GitHub 404` during `registry:sync` can mean missing authorization or a nonexistent ref/path: verify the personal account, allowed source and exact commit without relaxing integrity checks. Do not claim live registry verification from an unauthenticated or mocked build.
- Use the personal identity for this repo (`ygrip <yunaz.gilang@gmail.com>`) for both author and committer, and push with the `github.com-personal` SSH host. Confirm authenticated API login is `ygrip`; the default `gh` account is different. Do not switch global authentication or expose credentials.

## Private-source credentials

Read [docs/registry-auth.md](../../../docs/registry-auth.md) from the repository root. Credentials belong only to Node registry-sync/build environment variables. Resolution is repository override → owner mapping → `TOOLS_GITHUB_TOKEN` → `GITHUB_TOKEN` → anonymous; explicitly configured missing secrets must fail closed. Configure read-only PATs or GitHub App installations without placing literal secrets or private keys in manifests, tool bundles, browser environment variables or committed configuration. A private source repository does not make its published JavaScript or repository provenance private.
